## 任务（占位接口见 `concurrency/mvcc.h`）

| 组件 | 说明 |
|---|---|
| 时间戳分配 | Begin 拿读时间戳、Commit 拿单调递增提交时间戳 |
| undo 版本链 | 每次更新把旧值追加进 undo log，版本链挂在 RID 上 |
| 快照读 | 按 `read_ts` 回放版本链，重建事务应当看到的那个版本 |
| 可见性判断 | 未提交数据对其他事务不可见 |

## 测试

`test/concurrency/mvcc_test.cpp`，共 5 个用例：

| 用例 | 覆盖点 |
|---|---|
| `TimestampsMonotonic` | 读/提交时间戳的分配顺序：新事务的快照包含上一次提交 |
| `SnapshotReadStable` | 快照隔离：戴上"眼镜"后，写者的新提交对读者不可见 |
| `VisibilityBoundary` | 可见性边界 `commit_ts <= read_ts`：恰好可见与刚好不可见 |
| `DeletedVersionInvisible` | 墓碑也是一种版本：删除在快照之后不生效，在快照之前生效 |
| `ConcurrentCommitSerialization` | 多线程并发分配提交时间戳：无重复、单调 |

## FAQ

**Q: read_ts 为什么取"最近一次已提交的 commit_ts"，而不是自己分配一个新号？**
A: 取已提交的最大值意味着"眼镜戴上的瞬间快照定格"——此后别人的提交都大于这个值，天然不可见。若自己分配新号，会和并发提交的号交错，可见性判断就乱了。

**Q: 版本链为什么挂 RID、且按新 → 旧排列？**
A: RID 是行的物理身份，更新只换版本不换身份，链子才接得住。回放是从新往旧找**第一个** `commit_ts <= read_ts` 的版本——大多数快照较新，从新端开始走最短路径。

**Q: 墓碑（is_deleted）为什么算一种版本而不是把链删掉？**
A: 删除对旧快照必须"不生效"——老读者还要读这行。所以删除同样带时间戳入链；只有当没有任何活跃快照可能再看到旧版本时，链才可以物理回收（HDB 不要求实现 GC，可作讨论）。

**Q: 这个实现和真实数据库的 MVCC 差在哪？**
A: 只处理已提交版本的可见性；未提交写入的暂存机制可参考 BusTub 的 `TXN_START_ID` 偏移技巧（把未提交时间戳加上一个大偏移，读时天然跳过），作为拓展写进报告。
